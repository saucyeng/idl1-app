## Findings

| Critical | `model/viewport.ts` — `transformFor`, the `translateXPx` line | `transformFor`'s translate term divides by the **rendered** viewport's µs-per-pixel (`usPerPixel`, computed from `renderedSpanUs`) instead of the **current** viewport's. This is correct only when `renderedSpanUs === currentSpanUs` (pure pan) or when `current.startUs === rendered.startUs` (which is only true for a zoom anchored exactly at `pixelX = 0`) — i.e. it happens to pass all three of this commit's `transformFor` tests, none of which combine a span change with a non-zero start shift. For any real zoom not anchored at the chart's left edge (the normal case — the wheel handler zooms at whatever `pixelX` the cursor is over), the live CSS transform misplaces the picture. Verified by direct execution: `rendered = {0,1000,100}`, zoom-in 2x anchored at `pixelX=100` (right edge) via `zoomAt` gives `current = {500,1000,100}` (correctly keeping the anchor at pixel 100 per `zoomAt`'s own, separately-correct math); `transformFor(rendered, current)` returns `{scaleX:2, translateXPx:-50}`, which maps `current.startUs` (should render at pixel 0) to pixel **50**, and `current.endUs` (should render at pixel 100, under the pointer) to pixel **150** — a 50px error, sliding the "instant under the pointer" 50px away from the actual pointer position while the gesture is live. This directly contradicts the doc comment's own claim ("keeping that instant fixed under the pointer") and design §6/C3 §4's zoom contract for the in-gesture visual, even though the settled `zoomAt` state itself (checked separately, both algebraically and by the existing tests) is correct. Confirmed by CSS transform-list semantics (`translateX(t) scaleX(s)` composes as `new_pos = s·x + t`, matrix-multiplication order, matched against `ChartCell.tsx`'s actual `transform: translateX(...) scaleX(...)` string) and by re-deriving `translateXPx` algebraically: the correct divisor is `currentSpanUs / pixelWidth`, not `renderedSpanUs / pixelWidth`. | Compute `translateXPx` using `current`'s own µs-per-pixel (`currentSpanUs / current.pixelWidth`), not `rendered`'s: `translateXPx = -(current.startUs - rendered.startUs) / (currentSpanUs / current.pixelWidth)`. Add a test that zooms away from `pixelX = 0` (e.g. anchored at the right edge or a mid-point) and asserts `current.startUs`/`current.endUs` land at pixel `0`/`pixelWidth` after applying the returned transform — the three existing tests are all degenerate cases that mask this bug. Small, mechanical, localized to one line plus a missing test case. |
| Important | `components/ChartCell.tsx:161-183` (`onSettleRef.current`) | No stale-settle guard. Two settles can be in flight concurrently if the user gestures again before the first settle's `ensureTiles(...).then(...)` resolves (plausible under real fetch latency). Whichever promise resolves **last** wins the call to `onViewportSettled`, even if it is the older, already-superseded settle — this can snap the parent's `viewport`/`tiles` (and, via the `useEffect` syncing `liveViewport` to the `viewport` prop, the live picture) backward to a stale window after a newer gesture has already settled forward. The task's own review brief flagged this exact question ("is there a stale-settle guard so an older settle's tiles cannot overwrite a newer viewport's?") and the answer is no — nothing compares `next` against the live/most-recent settled viewport before calling `onViewportSettled`. This is a real, reachable race, distinct from the already-honestly-documented `TODO(idl0)` about a mid-flight cache eviction (that one is acknowledged in a comment; this one is not documented anywhere). | Tag each settle with a generation counter (or capture the latest `notify`-ed value and compare identity/deep-equality before committing), and drop `onViewportSettled` calls whose `next` is not the current latest settled/live viewport, mirroring the "stale response" guard the standing review brief's IPC-effects section already requires for other IPC-driving code in this lane. |

## Verdict rationale

The debounce mechanism (`settle.ts`), the clamp/pan/zoom state math (`clampTo`/`panBy`/`zoomAt`), the P3/P4 wiring (no IPC reachable from any gesture-frame handler, `ensureTiles` reachable only from the settle callback), the honest `hover.ts` TODO closure, and all hygiene/ownership/testing-format checks are correct and well-documented. However, `transformFor` — the function that renders the *visible, in-progress* picture during every zoom gesture — has a confirmed, reproducible arithmetic bug: it divides the translate term by the wrong viewport's pixels-per-µs, so any zoom not anchored at the chart's own left edge (the ordinary case) visually mispositions the picture during the gesture, contradicting the stated "keeps that instant fixed under the pointer" contract. All three of this commit's own `transformFor` tests happen to fall into the two degenerate cases where the bug is invisible, so the gate passing does not indicate correctness here. This is a real, shipped-behaviour bug (Critical) with a small, one-line, mechanical fix plus one missing test case, alongside a second, lower-severity but real correctness gap (no stale-settle guard, Important) that the review brief specifically asked about and that the code does not address. Approach and structure are otherwise sound — this is a fix-up, not a rework.
