| Important | `ChartCell.tsx:318` (`handlePointerMove`, `cursorDriverRef.current.notify(viewport, pixelX)`) | `notify` is given the component's settled `viewport` **prop**, not `liveViewport` (the local state that tracks the picture's current position during an active drag/zoom gesture — the same value `transform = transformFor(viewport, liveViewport)` uses to render the live-panned picture). During any drag, `viewport` stays at its pre-drag value until the tile-fetch settle later updates it; `pixelX`, meanwhile, is the pointer's current on-screen position against the *live* (panned) picture. So a pointer pause mid-drag debounces to `dispatch(viewport_stale, pixelX)`, computing a `t_us` for a time window the picture is no longer actually showing at that pixel — a request that answers the wrong question. In practice this is masked, not absent: `handlePointerMove`'s dragging branch resets **both** `cursorDriverRef`'s `notify` timer and `settleRef`'s tile-settle timer on every move, and both delays are `150` (`CURSOR_SETTLE_MS` in `cursorReadoutDriver.ts`, `SETTLE_DELAY_MS` in `ChartCell.tsx` — two independently-declared literals, not a shared constant), so the wrong-viewport dispatch's `seq` is essentially always superseded by the tile-settle's correct `dispatchNow(next, ...)` dispatch before the wrong one's fetch resolves, and `isStaleSettleResult` drops it silently. The masking is a coincidence of two unrelated magic numbers matching, not a designed invariant — if either constant is retuned independently in a future task (a plausible, unflagged change neither file's doc comment warns against), the two timers drift apart and the readout will visibly flash (or briefly settle on) a value computed against the wrong time window during a drag pause, then self-correct once the tile settle catches up. | Pass `liveViewport` (not `viewport`) to `cursorDriverRef.current.notify` in `handlePointerMove`, so the pointer-stop settle always computes `t_us` against the picture the user is actually looking at, independent of whether the tile settle's timer happens to be running in lockstep. |

## Checks performed (all pass)

- **review-task9.md Critical (RasterUnderlay self-cancel) — closed.** `fetchRaster`/`fetchRasterMeta` no longer appear in any re-run condition: the effect has no dependency array at all (runs every render) and is a no-op unless `rasterFetchKeyEquals(dispatchedKeyRef.current, key)` is `false`; the two function props are held in `fetchRasterRef`/`fetchRasterMetaRef`, updated unconditionally every render, and read only via `.current` inside the effect body — an unrelated re-render that only hands a fresh closure identity for these two props changes neither `key` (they aren't fields of `RasterFetchKey`) nor the refs' *behaviour* (only their pointed-to closure, transparently), so it can never trigger the `if` branch. Confirmed `RasterFetchKey` (`model/rasterLayer.ts`) has no function-typed field. There is no cleanup function in the effect at all — nothing to cancel — matching the doc comment's claim.
- **Staleness via monotonic epoch, and epoch-before-fetch ordering.** `epochRef.current += 1; const dispatchEpoch = epochRef.current;` runs immediately before `rasterRequestFor`/`Promise.all([fetchRasterRef.current(...), fetchRasterMetaRef.current(...)])` — the bump happens before the fetch is issued, so a fetch that starts sees its own already-incremented epoch and a subsequent dispatch's bump strictly exceeds it. `.then()` checks `isStaleSettleResult(dispatchEpoch, epochRef.current)` (Task 8's pure `!==` comparison, already tested in `settle.test.ts`, correctly reused rather than re-implemented) and drops the result on a mismatch before touching the canvas.
- **`rasterFetchKeyEquals` cost per render.** Cheap: eight `===` field comparisons plus one `JSON.stringify` per side on the small, kind-specific `params` object (`SpectrogramParams`/`Histogram2dParams`, no function/`undefined` fields) — a handful of primitive fields and two short-string allocations per render, not a hazard given chart cells re-render at UI, not per-frame gesture, rates for this effect (the gesture path itself never touches this component's re-render — `viewport` only updates on settle).
- **Device-pixel sizing.** Backing store: `width={Math.round(width * devicePixelRatio)}`, `height={Math.round(height * devicePixelRatio)}` — device px. CSS box: `style={{ ..., width: `${width}px`, height: `${height}px`, ... }}` — unchanged, CSS px, so the element's on-screen footprint is untouched. `ctx.setTransform(devicePixelRatio, 0, 0, devicePixelRatio, 0, 0)` is called in the `.then()` right before `drawRaster`, after first resetting to identity (`setTransform(1,0,0,1,0,0)`) and clearing in the canvas's own device-px space — so `drawRaster`'s CSS-px-oriented rect (per `alignRasterToAxes`'s own doc comment) draws correctly scaled onto the device-px buffer. This closes review-task9.md's Important finding.
- **`makeCursorReadoutDriver` — CURSOR_SETTLE_MS.** Named constant (`export const CURSOR_SETTLE_MS = 150;`), doc comment states its unit (ms) and purpose (design §6, R62).
- **`notify` issues no IPC.** `notify(viewport, pixelX): void { settle.notify({ viewport, pixelX }); }` — only calls `makeSettle`'s own `notify`, which stores the latest value and (re)arms a `setTimeout`; no call to `deps.fetchCursorReadout` or any IPC-shaped function reachable from `notify` itself, confirmed by reading the whole module (the only two call sites of `deps.fetchCursorReadout` are inside `dispatch`, which only `notify`'s *debounced callback*, `dispatchNow`, and `leave`'s prior state (not directly) reach).
- **One request per settle window.** `makeSettle`'s own arm/disarm semantics (already tested in `settle.test.ts`, reused unmodified here) collapse repeated `notify` calls within `delayMs` into exactly one `dispatch` call using the latest value — `cursorReadoutDriver.test.ts`'s first test (`"two notifies within the window — dispatches once, for the latest position"`) exercises this directly against the real driver and asserts `fetchCursorReadout` called exactly once, with the second (`600`) position's `tUs`.
- **`dispatchNow` shares the sequence.** `dispatchNow(viewport, pixelX): void { dispatch(viewport, pixelX); }` — calls the same `dispatch` function `notify`'s debounced callback calls, which does `seq += 1; const seqAtDispatch = seq;` at its top — the same module-scoped `seq` counter, so a `dispatchNow` call always produces a strictly higher sequence number than any earlier `notify`-driven dispatch, and vice versa; there is exactly one `seq` per driver instance, confirmed by reading (no per-path counter).
- **`leave()` cancels the pending timer.** `7785b73`'s diff adds `settle.cancel()` as `leave`'s first statement (previously only `seq += 1; deps.onState(null)`), calling `model/settle.ts`'s own `cancel()` (clears the timer handle via the injected `SettleTimer.clearTimeout`, matching `settle.test.ts`'s established `cancel` semantics) — a `notify` scheduled just before `leave()` can no longer fire afterward.
