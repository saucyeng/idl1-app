## Findings

| Severity | file:line | Finding | Fix |
|---|---|---|---|
| Important | `core/src/store/import.rs:150-153` | `import_idl0` calls `blob::write_blob(data_root, bytes)?` **before** `crate::parse::parse(bytes)?`. Per the lead's ordering ruling (an unparseable `.idl0` file must leave nothing in the CAS), this is backwards: a file that fails `parse::parse` (bad magic bytes, unsupported schema version, or too-short-for-header truncation) still gets its raw bytes written into `blobs/sha256/...` first, leaking an orphan blob with no session ever referencing it. `verify` has no orphan-blob check (`store/verify.rs` implements #1-5/#8/#10, not blob-orphan detection), so these leaked blobs are silent and permanent — nothing in this lane prunes `blobs/`. No test exercises or catches this (there is no test asserting a bad-magic-bytes buffer leaves the blob store untouched). | Reorder: call `crate::parse::parse(bytes)?` first (it doesn't need the blob on disk — the hash is computed from `bytes` directly, independent of parsing), and only call `blob::write_blob` after a successful parse. Add a unit test that a bad-magic-bytes buffer produces `Err` and `blob::blob_exists(data_root, &expected_hash)` is `false` afterward. |
| Minor | `core/src/store/parquet.rs:361-397` (approx.) | `read_session_parquet` now calls `read_session_metadata(path)` and then re-opens the same file and re-parses the Parquet footer a second time (`ParquetRecordBatchReaderBuilder::try_new` is invoked twice for one read). Not incorrect and not what the plan/R18 asked to fix (the ask was "one parser, not two", i.e. one code path for the nine keys, which is satisfied), but it is a small avoidable double footer-read on every session read. | Have `read_session_parquet` reuse the already-open `builder`'s metadata (`builder.metadata()`) to extract the key-value pairs instead of calling `read_session_metadata` (which does its own `File::open`), or have `read_session_metadata` accept an already-built reader. Not blocking. |
| Minor | `core/src/store/import.rs:238-242` (`cmd_import`'s `unreachable!()` for `ImportPlan::Collision`, mirrored in `cli/src/main.rs`) | `ImportReport::plan` is typed as `ImportPlan` (four variants) even though `import_idl0` provably never returns `Ok(ImportReport { plan: Collision, .. })` — the doc comment says so and the CLI match arm is a documented `unreachable!()`. Not a bug, just a slightly wider type than needed (a 3-variant "executed" enum would make the impossible state unrepresentable instead of documented-unreachable). | Optional: split into `ImportPlan` (planning, 4 arms) and a separate `ExecutedPlan { Write, Skip, Regenerate }` for the report, removing the `unreachable!()`. Not required — current approach is honest and documented. |
