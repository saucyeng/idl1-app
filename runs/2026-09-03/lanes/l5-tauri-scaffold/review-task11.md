## (a) R47's root-cause fix — the `resolved` cross-reference overlay

`resolve_workbook_defs`'s `deps` and `results` maps are correctly re-keyed to `DefKey = (cell_id, name)` (`resolve.rs:95,134-166,205-215`), and `math_cell_defs`'s `.remove(&key)`/`.expect(...)` in `eval.rs` is re-keyed identically — verified both maps, not just one; a duplicate name in two cells can no longer collapse either map to one entry, and the `.expect()` that used to panic on the second cell can no longer find a hole (`eval.rs:126-149`). This is a real fix, not just a rename: traced through the two-cell duplicate case by hand and confirmed both cells' `MathCellDef`s now get independent `deps`/`results` entries regardless of name collision.

The one thing deliberately left name-keyed — the internal `resolved: HashMap<String, (...)>` overlay used to serve `[Name]` cross-references from a *third* definition — is **not safe in the sense the reviewer was asked to check**, though the risk is bounded and disclosed:

- `remaining` is a `Vec<&MathCellDef>` built from `defs.iter().collect()` (document order), and each fixed-point pass iterates it in that order, so which of two same-named definitions last writes `resolved[name]` is **deterministic given the document's content** (not run-to-run random) — but it is **order-dependent** in two compounding ways: (1) if the two duplicates become *ready* in different fixed-point passes (because one has more dependencies than the other), the one that resolves in the *later* pass always wins, regardless of document position; (2) if they become ready in the *same* pass, whichever comes later in `defs`' Vec order (i.e., later in the document) wins.
- Concretely: reordering two cells that both define `x` — an edit a user could make for readability, with no other change — can silently flip which cell's `x` a third cell's `[x]` reference resolves to. Nothing surfaces this: the document still carries the same `workbook_duplicate_definition` structural error before and after, so there is no user-visible signal that the *value* seen by a dependent definition just changed.
- The doc comment added in this fix (`resolve.rs:96-113`) honestly discloses this exact ambiguity and reasons that C2 §3.5.A's `DuplicateDefinition` already flags the document as invalid, so a well-defined answer for the dependent isn't this fix's job. That is a defensible position — the `DuplicateDefinition` state is already an error a user must fix — but it is still an *order-dependent* answer to the question asked, and R47 itself doesn't rule on it (R47 only mandates that both duplicates keep their own result, which is done correctly).
- No test exercises a third definition cross-referencing a duplicated name at all — only the "both cells get their own value" case is tested (`resolve.rs`'s new test, and `eval_workbook`'s command-level test). A future refactor of the fixed-point loop could silently change which duplicate wins with no test catching the change.

This is worth a lead ruling or at minimum a `// TODO(idl0):` pinning the current tie-break rule with a regression test, not a blocking defect — the underlying document state is already flagged invalid, and per-cell defs still each carry their own correct value.

## (d) R48 — `sanitize_file_name_stem` and the new-workbook path

`sanitize_file_name_stem` (`commands/workbook.rs:174-179`in the diff) maps every char outside `[A-Za-z0-9 _.-]` to `_`, then trims leading/trailing `.`/whitespace, falling back to `"workbook"` if empty.

- **Path traversal:** both `/` and `\` are outside the allowed set and become `_`, so a name like `../../etc/passwd` sanitises to `.._.._etc_passwd` then trims to `.._.._etc_passwd` (no leading dot after the second underscore) — no directory separator survives, so it cannot escape `workbooks/`. A name of exactly `..` sanitises to a string that trims to empty (both dots are trim chars) and falls back to `"workbook"`, so a bare `..` doesn't produce a `..` path segment either. This part is correct.
- **Reserved Windows device names** (`CON`, `PRN`, `AUX`, `NUL`, `COM1`–`COM9`, `LPT1`–`LPT9`) are **not special-cased** — a workbook named e.g. `CON` sanitises to `CON` and would attempt `workbooks/CON.idl1wb`. I verified empirically on this machine (Windows 11, build 22621) via `[System.IO.File]::WriteAllText` (the same Win32 `CreateFile` path `std::fs::write`/`std::fs::rename` uses) that both `CON.idl1wb` and even bare `CON` succeed as ordinary files with no special device redirection — current Windows has relaxed this restriction for regular file creation outside console-redirection contexts. So this is not a live bug on the target OS as tested, but it is unhandled defensively and the failure mode on an OS/config where it *does* matter (older Windows builds, or paths that hit a legacy code path) would be an opaque `io` error from `write_atomic`, not a clear message. Minor, not Important, given the empirical result — but worth a one-line comment or guard given SPEC §15.1's convention is silent on this and C4 §2 doesn't rule it out either.
- No core sanitiser existed to reuse (confirmed: `session::filename::unique_file_base` only does the collision-suffix half, has no sanitisation of its own) — the brief's "scoped to workbooks" framing is accurate, and `unique_file_base` is reused correctly for the `-2`/`-3` suffix (verified against SPEC §15.1's convention).
- The collision test (`save_workbook_creating_two_new_workbooks_with_the_same_front_matter_name_the_second_gets_a_collision_suffix`, `commands/workbook.rs:574-594`) is a genuine two-distinct-id, same-display-name collision, not a same-workbook double-save — confirmed by reading the fixture (`WB_ID` vs a second UUID, both named "Fork tuning").
- `id` never names a file: `save_workbook_via`'s path-resolution only falls through to the sanitised-name branch when `resolve_workbook_path(data_dir, id)` fails **and** `based_on_hash` is `None` (Step 2, `commands/workbook.rs:296-316`) — a `based_on_hash: Some(...)` against an unresolvable `id` correctly returns the `not_found` error instead of silently creating a file, matching R48's ruling that `id` never names a file.

## (f) Watcher lifetime

`Watchers` (`state.rs`) is a `Mutex<HashMap<String, WorkbookWatcher>>`; `watch_workbook`'s command wrapper does `watchers.0.lock().unwrap().insert(id, watcher)` (`commands/workbook.rs:445`) — `HashMap::insert` on an existing key drops the old value before installing the new one, and `WorkbookWatcher`'s only field is `notify::RecommendedWatcher` (`watcher.rs:68-70`, untouched by this diff), whose own `Drop` tears down the OS watch handle — so **re-subscribing to the same id does not leak**; confirmed by reading `notify`'s `RecommendedWatcher` is the platform watcher type whose drop unregisters it, not by taking the doc comment's word for it.

In an ordinary session opening (and closing, without ever re-`watch_workbook`-ing) twenty distinct workbooks: each gets its own `WorkbookWatcher` entry in `Watchers`, keyed by a distinct id, and **none of them is ever dropped** for the app's lifetime — there is no unsubscribe command (correctly disclosed, per the brief's own ruling, in the TODO, the doc comment, and the CHANGELOG line "No unsubscribe in wave 1"). This is a bounded leak (bounded by the number of *distinct* workbook ids ever opened in a session, not unbounded per remount) of one background OS file-watch registration and one background debounce thread each, all pointed at the same non-recursive `<data>/workbooks` directory — in an ordinary session (tens of workbooks, not thousands) this is unlikely to be user-visible, but it is a real, disclosed cost of the wave-1 design, not a defect introduced silently.

C4 §4's self-write suppression is unaffected by watcher replacement: the `ExpectedHashSet` behind `Hashes` is a single object in `app.manage(...)`, shared by reference (`Arc<ExpectedHashSet>`) across every `WorkbookWatcher` and every call to `save_workbook` — it lives independently of any individual watcher's lifecycle, so dropping/replacing a `WorkbookWatcher` entry never touches the hash set that suppresses self-writes. Confirmed by reading `watch_workbook_via`'s signature (`hashes: Arc<ExpectedHashSet>` passed by clone from `Hashes` state) and `save_workbook`'s command wrapper (`hashes: tauri::State<'_, Hashes>`) both deriving from the one `app.manage(state::Hashes(Arc::new(...)))` call in `app/src-tauri/src/lib.rs`.
