## Priority 1 — flaky test verdict

**Not a Task 10 regression.** `dc5388a`'s diff touches only `commands/device.rs`, `commands.rs`→`commands/mod.rs`, `lib.rs`, `Cargo.toml`/`Cargo.lock` — `watcher.rs` is untouched by this task. This is a **latent Task 3 issue**, exposed (not caused) by Task 10 simply adding 14 more `#[tokio::test]`s that run concurrently with the watcher tests' real OS file-watch threads, raising scheduler contention.

Root-cause read of `watcher.rs`: the watched-directory callback (lines 84–111) computes `sha256_hex(&bytes)` from a fresh `std::fs::read(&path)` on *every* filesystem event `notify` delivers for `target`, and treats a hash **mismatch** as "pending external change" (line 96, unconditionally inserting into `pending` before any debounce check). On Windows, a single `std::fs::write` can be observed by `ReadDirectoryChangesW`/`notify` as more than one event (the module's own doc comment on `ExpectedHashSet::check_and_consume`, lines 36–44, already acknowledges "`Create` then `Modify`, both carrying the final content" as an observed pattern). If an earlier event in that sequence is delivered before the file's bytes are fully flushed (more likely under the scheduling pressure of 8-wide parallel test execution), `std::fs::read` returns a short/empty read, its hash will not match the pre-registered expected hash, and that single early mis-hash is enough to seed `pending` and fire `on_external_change` ~100 ms later — even though a later, correctly-hashing event for the same self-write would have been suppressed. Nothing re-validates the *debounced* path's content against the expected-hash set at fire time (line 103–107 only checks path presence + elapsed time, not hash), so one bad early read is unrecoverable once `pending` is seeded.

This is real, narrow, and timing-dependent — recommend a **separate fix-up task**, scoped to `watcher.rs` only: either re-run `check_and_consume` against a fresh read of `path_for_thread` at debounce-fire time (not just at initial-event time), or debounce before hashing so only the settled bytes are ever hashed. Do not fold this into Task 10's own review outcome.

## Priority 2 — architectural concerns

1. **`push_config` schema validation gap**: acceptable wave-1 scope boundary. `idl_rs::config` has no `VersionedConfig` implementor for the device-config schema yet (that type is core's/L1's job, CLAUDE.md §7 forbids `rust/tauri` from defining it). The narrowing to well-formed-JSON-only is explicit, marked `// TODO(idl0):` (device.rs:247–249) in the correct form, and disclosed in both the module doc comment and the CHANGELOG entry. No objection.

2. **No persistent BLE connection state**: consistent with C3 §3.8 as written. Every command after `ble_connect` (`list_device_files`, `download_file`, `push_config`) re-takes `device_id: string` as its argument, not a connection handle or session id — if C3 intended a live session model it would thread a handle through those signatures instead. `ble_connect`'s `ConnectionInfo` reading as a snapshot is the natural implementation of that stateless contract, and the trade-off is disclosed prominently in the module's own doc comment (device.rs:15–23). No objection to the design; a live-status manager is correctly deferred to whichever UI task needs it.
