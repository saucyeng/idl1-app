# Flutter OTA flow (idl0-app) — extraction for idl1

Source: `idl0-app/app/lib/{ui/tabs/settings/firmware_update_section.dart, providers/{firmware_update_provider,device_provider}.dart, transport/{firmware_catalog,wifi_transfer,ble_service}.dart, data/exceptions.dart}`.

## 1. Flow
Auto-check on load if connected+enabled (`firmware_update_section.dart:124-130`) or manual "Check now"/channel switch (`:747-751,726-729`). Compares device version to GitHub Releases `latest(channel)` — stable=`/releases/latest`, beta=first non-draft of `/releases` (`firmware_catalog.dart:103-135`). "Update to vX" downloads `.bin` (progress + optional sha256 verify) then auto-pushes (`:144-178,184-227`), or user picks a local `.bin` via file_picker (`:50-59,184-199`). Push (BLE-connected only, `:442`) auto-drives WiFi mode up if needed, awaits proxy bind, `POST /ota` streams bytes (`wifi_transfer.dart:311-373`). Progress bar + Cancel (`:524-548,313-318`). On success: device reboots, app pauses auto-connect, arms one-shot confirm (catalog releases only), shows "rebooting" for 5s, retries reconnect (`:270-311,336-367`). On reconnect matching armed version + pending-verify, silently sends `CMD_OTA_CONFIRM` (`device_provider.dart:253-299`). Otherwise a persistent card offers manual Confirm/Roll-back instructions (`firmware_update_section.dart:581-642`).

## 2. State machine
UI phase `idle→downloading→pushing→rebooting→idle` (`:70`); the pending-verify card is orthogonal, driven only by device status. Arm/one-shot (`device_provider.dart:138-173,253-299`): `armOtaAutoConfirm(version)` set on catalog push; disarmed on manual `.bin` pick (`:192`); consumed unconditionally on the first *connected* status frame carrying a version (prevents a stale arm surviving rollback, `:238-240`); fires `confirmOta()` only if that version matches and `otaPendingVerify` is set, swallowing `TransportException` (`:284-299`). The pre-`isConnected` handshake frame is deliberately skipped (`:243-252`). Reconnect: disconnect/clear, wait bootDelay (4s default, panel uses 5s), retry `connect()` up to 4x/2s (`device_provider.dart:322-341`, `firmware_update_section.dart:102,348-352`); give-up still resumes the background scanner (`:353-357`). Failure: HTTP 400 = corrupt image, 500 = device error, both reset phase to idle with `_picked` kept for retry (`:320-334,290-310`); a `SocketException` within ~5s of a 200 is the expected reboot signal, not an error (`:296-298`). No app-driven rollback — purely a power-cycle instruction (`:622-635`).

## 4. Preconditions / bugs flagged
BLE connected gates Push + version compare (`:442`, `firmware_update_provider.dart:124`). Device version must parse as semver else non-fatal `FirmwareCheckUnknown` (`:128-134`). WiFi mode entered automatically, proxy bind awaited before POST (`:214-251`). No explicit battery or recording-stopped check found in this file. Bugs/workarounds: manual `.bin` picks never auto-confirm — intentional, not a bug (`:112-116,196-198`); the handshake-frame skip is an explicit workaround for BLE subscribe-before-connect ordering (`:243-252`); progress reports bytes queued into the sink, not confirmed on-wire (`wifi_transfer.dart:329-332`).

## 5. Mapping to Rust transport
`POST /ota`: `pushFirmware` (`wifi_transfer.dart:311-373`) ≈ `WifiTransport::push_ota` (`wifi_transport.rs:132-134,297-308`). Missing in Rust: chunked/progress streaming, and 400-vs-500-vs-other discrimination (`error_for_status()` collapses all non-2xx). `CMD_OTA_CONFIRM` already wired (`ble_control.rs:14,77` `OtaConfirm=0x06`), matching Flutter's `confirmOta()` (`ble_service.dart:268-274`) — no confirm wrapper exists yet. `OTA: PENDING_VERIFY` parsing exists (`ble_status.rs:27,134` `ota_pending_verify`), matching `DeviceState.otaPendingVerify`. Missing entirely: the firmware catalog (GitHub Releases poll/compare/sha256 verify, no `rust/transport` or `rust/core` equivalent), and the app-layer reconnect-retry + arm/disarm auto-confirm state machine (§2), which belongs in `idl-rs-tauri`/`app/src`, not `rust/transport`.
