## A. The maths graph

38. A node is a **dataset**: every raw session channel is a source node, and every derived dataset (filter output, math channel) is one node that can be charted or wired into another node — because: "a node is a dataset; they start off as channels, then each filter or math channel creates a derived dataset".
39. One node may perform **several operations in one step** (e.g. a filter and a matrix multiply) so intermediate datasets never appear on charts unless the user names them — because: "to not muddy the chart".
40. The **workbook file is the source of truth; the graph is an editor over its math cells** (a view of `name = expr` lines, C2 §3), never a separate model — because: "the file is the source of truth and the graph is the pretty UI editor"; consistent with round-1 decision 20.
41. Node status is a small glyph on the card: **red × = errored, spinner = running, green check = evaluated**; an unresolved input (channel absent in this session) greys the card — because: "a small red x, spinner, green check would work well".
42. Plan for **~50 definitions** in a real workbook: the canvas ships with **search, a minimap, and subgraphs** — because: "I could imagine 50, so those features would probably be great".
43. **Subgraphs, KiCad-subsheet style**, are in scope for the maths lane's first pass: a bundle such as the iEKF is one interchangeable subgraph with named inputs and outputs — because: "the stuff like the iEKF can be its own interchangeable subgraph"; "ah, yes, if possible".
44. When the selected session lacks a channel, the node and everything downstream **grey out on the graph and on charts; nothing is hidden or removed**, and the switch is never refused — because: "otherwise channels might get lost due to a simple channel rename".
45. A node draws as a **small card: name, unit, the key parameters (filter cut-offs, window sizes) and the status glyph**; hovering shows the definition line, input names and sample rate; editing the expression happens in the properties column — because: "a little card, maybe the name, units, parameters like filter frequencies; hovering gets the math line itself".
45a. **Clicking a card opens the node's full details pane in the properties column**; adding from a raw channel, rewiring an input, changing a constant and renaming are all first-class and each is one gesture (drag from the channel list, drag a port, edit a field on the card, double-click the name) — because: "probably all of the above; a couple of details on the card, clicking into the card brings up the node's full details pane".
45c. **Node outputs are typed arrays of any dimension** — a series, one value per lap, a time×frequency matrix, an iEKF state vector — and **every kind can feed further maths**: a peak-frequency line derived from a spectrogram is a must; charts render whatever dimension makes sense for the mark — because: "the pictures definitely feed further maths; the peak frequency line is a must; the iEKF spits out state vectors with weird dimensions that everything else is based on". *Lead: C2 math definitions today yield 1-D channels and rasters are chart-side endpoints (design §4); this is a core/C2 extension (n-D values in the math language) and is the maths lane's first spec question.*
45b. **File mapping:** one node = one `name = expr` definition line; a multi-operation node is a nested expression on that line; a subgraph = one `math` cell named by `# label:`; canvas positions live in the file (C2 extension, lead's call) — because: "I think so" (accepted on the interviewer's recommendation).

## B. Selection and cross-tab state

46. Selection is **one app-wide state** (as `AppState.selection` today) and must grow to hold **more than one session** — session-to-session comparison is wanted, lap-to-lap will be the common case; both are the shared selection, not a chart-level property — because: "session to session is definitely preferred, though lap to lap will be more common; either way the state is carried app wide". *Lead: today's `Selection` has a single `sessionId`; this is a contract extension, not a UI-only change.*
47. Selecting a lap **re-evaluates every math definition over that lap and re-scopes every chart**; Device ignores selection; Data highlights it — because: "yup, recompute and show the graphs".
48. Nothing about selection survives a restart: the app opens with **no session or lap selected** and the **last-used workbook** open and empty of data — because: "only the workbooks themselves should persist, including the active one; don't worry about filling it with data".
49. The mental model is **one well-built workbook per discipline**, reused across a season; the app opens to the last one used — because: "I envision just having one really well built out workbook per discipline".
50. A finished device transfer **does not change the selection**; the transfer UI gets a per-session **"Analyze" button** that selects that session and jumps to the Notebook — because: "sometimes I'll be importing multiple at a time; a button to go straight from transfer to analyze".

## C. Time, cursors and linked views

51. The **cursor follows the pointer across every chart** in the worksheet; a **single click pins it** — because: "normally a cursor is following the pointer around on all channels and single clicking would place the cursor".
52. The **X range is shared by every chart in a worksheet**, with one exception: a **master timeline strip** at the top of the worksheet always shows the whole lap/session and carries the **draggable boundary cursors** that set the shared window — because: "shared x should be universal, maybe except for one master timeline that shows where the draggable boundary cursors are".
53. **Y ranges are per chart**; shared Y is deferred — because: "shared y is a no for now; very low priority".
54. **Time vs distance on X is a worksheet-level setting** (as idl0's TIME ▾), never per chart — because: "worksheet level might be more straightforward for now".
55. The cursor carries a **small card at the cursor showing each series' Y at that X**, one row per series and per overlaid lap; overlaid laps align by lap-relative time or lap distance according to the worksheet's X mode — because: "a small card/tooltip showing the y value at that x/t; alignment depends on time or distance mode worksheet wide".
56. **Hover shows values only; drag zooms to the dragged region; click pins the cursor.** There is no separate "scrub" gesture — because: "hover without clicking is just show the values; dragging should zoom into the dragged region".
57. **Playback:** speed is selectable; play **stops at the end of the lap**; the window **scrolls when the cursor reaches its edge**; a second, user-selectable mode keeps the **cursor fixed and the charts pass under it** — because: "yes on speeds; stop at the end of the lap; yes on scroll; I kind of want the option to have the cursor sit in the same spot and have the charts pass by".

## D. Errors, staleness and trust

58. A chart whose input definition **errors** shows an **empty slot with the error message and a "Fix" button** that opens the broken definition's node/properties — because: "the empty slot with a message and the button to fix the broken channel/properties".
59. A **stale** result (dependents of a definition just edited, not yet re-evaluated) stays on screen **greyed with a spinner over it** until the new result replaces it; a chart never blanks while recomputing — because: "a spinner over the greyed out stale data".
60. **Gaps and burst-seam corrections are visible on charts** as a faint hatched band over the affected X span, if the tile stats make it cheap; otherwise a diagnostics view carries it — because: "assume a soft yes for now if it's not too complicated".
61. **Nothing shows data outside the current selection.** Unchecking a lap or session empties every chart, table and inline value that depended on it, immediately; no view keeps a previous lap's data for continuity — because: "pretty much everything — uncheck a lap and it all disappears is the idea".
62. An **engine or importer version change** that will regenerate derived files is announced by a **dismissable banner** on the workbook, not a toast or silence — because: "a banner for now so it can be temporarily ignored".
63. *(interviewer's call)* An inline prose `${…}` value whose definition errors renders as an `--accent` `⚠ name` marker with the message on hover; it never renders a stale number.

#### Amendments from the errors-and-staleness lane (2026-09-13, spec-during, W3.3 row E)

- **58 — the empty slot is the size the chart would be.** The slot's height floor now tracks the chart's own default height rather than the height one line of note text needs. A cell that is a chart with a session selected and a note without one otherwise moved everything below it up the page as the selection changed, which is the layout jump the decision exists to prevent. A chart taller than the floor keeps its own reported height. `model/jsCellFrameHeight.ts`.
- **59 — `stale` is a state, not a flag on `evaluating`.** `CellStatus` gains a fifth value. A cell with a result on screen that the latest edit made out of date is `stale`; a cell evaluating for the first time is `evaluating`. Both spin; only `stale` is washed grey, because `evaluating` has nothing on screen to grey and a wash over an empty box would claim blank space is old data. `stale` is the same state during the edit debounce as during the round trip, so a recomputing cell does not flicker between two waiting pictures a few hundred milliseconds apart. `model/cellStatus.ts`.
- **60 — gaps ship; burst seams do not.** The decision's "if the tile stats make it cheap" is answered **yes for gaps**: C3 §3.5's decoded tile already carries `COLUMN_T_US_EMPTY` at every pixel column whose bucket range holds no sample, so a run of sentinel columns is a recorded gap read off data the chart has already fetched — no new field, no second round trip, no engine change. Runs reaching the first or last column of the tile set are dropped: those are the fetched range's edge, not a gap. **Burst seams are not covered.** C1 §3.3's correction records only its algorithm version (`seam_correction_version`), and a corrected seam has samples on both sides so it leaves no sentinel behind. Making seams visible needs a C3 field — a `seams: {start_us, end_us}[]` on the session-detail response, or a seam region in the tile payload — which is a contract change and is **open**. `model/gapSpans.ts`, `--gap-hatch`.
- **61 — an empty selection outranks every other cause.** It used to be checked last, on most-specific-wins. That was wrong once nothing was selected: with no session there are no session channels to resolve against, so every referenced channel came back unresolved and the cell claimed the channel was "not part of this session" — naming a session that does not exist, about a reference that is very likely fine, beside a Fix button that would open a correct definition. A cell making no channel call at all still gets no note: it never depended on the selection (R148). `model/jsCellNote.ts`.
- **62 — the workbook half, and what writes it.** Alongside the per-session engine-version banner already shipped, the workbook records the build that last evaluated it in an advisory `evaluated_with` front-matter key, announced as "Evaluated with idl1 X.Y; you are on X.Z" with a **Re-evaluate** action. No contract change is needed for the key to be safe in a file: R135 (C2 §3.2) makes a v3 parser preserve every top-level key it does not define, and the key is advisory exactly like C2 §3.7's `graph`. **Nothing writes it yet** — "never auto-rewrite the file" is taken at its word, so Re-evaluate re-runs the evaluation and leaves the recorded value alone. Stamping the key on an explicit save belongs in `core`'s `render_front_matter`, a Rust change, and is **open**. Versions are compared as exact strings, never ordered.
- **63 — the marker also covers "nothing selected".** An unresolved span used to fall back to the raw `${expr}` template text, which this decision forbids outright. With nothing selected no result can ever arrive, so the span now gets the same marker an errored one gets, naming the Data tab on hover. A span merely waiting on its first evaluation *with* a session selected keeps the placeholder — marking that would flash a warning across every prose block on every workbook open. The glyph stays `⚠` as written here; the lane brief's "✕" was not adopted, since `✕` is R216's cell-status glyph and reusing it for an inline value would conflate the two vocabularies.

## E. Device tab refinements

Walks `runs/2026-09-05/QUESTIONS-FOR-ISAAC.md` item 12.

64. The hero-card dropdown becomes a **real device picker**: lists every discovered idl0, connects to any of them, and lets the user **switch between two devices in the field**; the app **auto-connects to the last-used device on launch** — because: "multi-device operation in the field didn't work; I wasn't able to search for and connect to the second device"; "open the app, it connects automatically".
65. The **RX/TX activity pair ports as-is**, distinct from the recording pulse — because: "port as is".
66. The recording timer uses a **device-reported start time**, not the client's first `logging:true` — because: "nope, I want the device reported one". *Lead: needs a firmware/status field (SPEC §7/§8); cross-lane.*
67. The **calibration panel is not ported**; a calibration routine is designed from scratch later; remove the placeholder — because: "don't port it; we need to come up with a good calibration routine from scratch".
68. HRM search **filters to the heart-rate service by default, with a "show all devices" toggle** — because: "default to filtered with a toggle to see all".
69. Push config **reads the device mode first** and refuses with a clear message before sending, instead of surfacing the device's rejection — because: "read mode first sounds wise".
70. **An IMU's six channels are all-or-nothing**: enabling an IMU enables all six; there is no per-channel checkbox inside an IMU. Per-IMU *settings* (rate, range, and the new 320 g IMU options) stay individually configurable — because: "they're all 6 or nothing; I had sessions where two of the IMUs didn't have all their channels"; "we have additional settings with the new 320 g IMUs".

## F. Philosophy: constraints lanes are held to

71. **Never lose a recording.** Nothing the app does — update, crash, disconnect, tab switch — may discard a recording on the device or a partially transferred file — because: "lose a recording is obvious".
72. **Recording and transfer are appliance-grade:** predictable, no prompts or questions mid-operation, no re-layout under the thumb, no network dependency; failures there are shown immediately and loudly. Analysis failures are inline and non-blocking (section D) — because: "it just needs to be predictable and work like an appliance"; "recording and transfer should be pretty bulletproof".
73. **The field loop must stay at its current click count:** open → auto-connect → record → stop → Files → check → upload. Any Device-tab change that adds a step to this loop is rejected — because: "some of the core workflows worked with very few clicks; the actual recording and transferring of files was great".
74. **Remember per device:** rider, bike, and later a bike setup sheet that changes over time; **propose the venue automatically** from GPS against known tracks/venues, never guessing silently — the user confirms — because: "per device it should remember the rider, bike, and eventually a setup sheet; I would love if it could figure out venue automatically".
75. **Workbooks are durable across app updates:** an update never deletes, silently rewrites or fails to open a workbook; any migration is explicit, keeps the original, and reports what changed — because: "there were a few times that I'd update the app and lose my notebook, so I didn't put that much effort into it; having the notebooks properly durable with updates will be important".
76. **Setting up a math channel must be cheap** — the maths graph exists because idl0's editor was "too tedious to set up math channels"; the lane is measured by the number of gestures from raw channel to charted derived channel.
77. The maths and chart editors should **work on mobile as far as the Properties form allows** (round-1 decision 29: Properties form as a sheet on narrow; the graph canvas is desktop) — because: "maybe try and make the maths and charts editor work on mobile".

## G. Gaps found by walking each lane's first day

78. **Per-bike calibration** aligns every sensor into one baseline reference frame before any maths runs: captured by an **in-app wizard** (≈10 s at rest on level ground), applied automatically to every session from that bike, with **bad-calibration detection** and a **buried menu to re-apply a new calibration set to past sessions** — because: "what I did was record a 10 s session at rest and told my agent to apply it; realistically we make that automatic with a wizard; bad calibration detection; a buried menu to edit after the fact".
79. The **bike sheet is a living entity with a versioned instance tied to every session** — setup data (and possibly the calibration matrix) — and is an **input node to the maths graph** — because: "its own living animal with an instance that gets tied to every session, as it'll evolve; an input to the maths map".
80. **Metadata capture is seamless and prompted:** rider, bike, venue, notes are pre-filled from what the app remembers per device (decision 74) and the user is **gently prompted, Strava-style, as soon as the session exists — not only after transfer** — because: "I needed to transfer them before I could jot my fast notes down, it didn't remember the data it should have, and I should have been gently prompted for it".
81. **As few files as possible** carry session metadata; the user never manages calibration or setup as separate files — because: "seamless metadata input and transfer, in as few files as possible".
82. **Subgraphs can be shared across workbooks** (the iEKF tuned once serves the MTB and moto workbooks); low priority, the option must exist — because: "I don't want to repeat it across my mtb and moto workbooks".
83. **Node → chart, two gestures:** drag a node's output port into the notebook column, or a "chart" button on the card; either opens the **chart-type selector with idl0's chart-type pictograms carried over** — because: "both; my chart type selector was really pretty, I want those small chart type images to carry over".
84. **Sessions on a shared chart are told apart by colour, chosen per session in the Data tab; line style is an addition**, and per-channel colour (round-1 decision 26) still applies within a session — because: "probably color, but line type would be a great addition; sessions get a color picker in the data tab".
85. **The report is a PDF of the notebook in its paper register**, sent to the rider or mechanic and read on a phone on the chairlift — a required deliverable, distinct from the deferred figure export — because: "a readable report that can be sent via pdf to the rider/mechanic". *Lead: round-1 decision 28 deferred figure export; report export is a new lane, wave order is yours.*
86. **N devices, simultaneous recording, fast switching:** the Device tab handles a list of connected devices (N is almost always 1, upper bound ~10), each recording independently, and switching the active device for download is one tap; sequential downloads from several riders must be smooth — because: "there's definitely simultaneous recording; two riders pull into the pits and need data downloaded sequentially; smooth with N devices".
87. **Live status during recording is per-IMU OK, GPS satellite count and recording duration — nothing more**, no live traces — because: "keep it lightweight on the ESP32".
88. A **venue is a named point with a radius**, assigned automatically on import the way track matching is; the user can rename or adjust — because: "named radius; pretty automatic; the track matching was automatic after all".
89. After upload, the **Analyze button (decision 50) runs the workbook against the new session and, once the agent lane exists, produces the report**; visible progress, latency accepted — because: "once the user clicks that, it should plug through the math and spit out the report; I'd expect it to take some time".

## Open

Isaac: "maybe stored on the device and hardcoded to each session"; "or keep them separate with the calibration in the binary file itself". Interviewer's recommendation: stamp it into the session on the device (it then travels with the blob and survives every sync), mirror it into the bike sheet for the after-the-fact re-apply path; the lead decides with SPEC §5/§8 in hand.
