| Major | `tauri/src/commands/rasters.rs` `fetch_fft_via` (~line 485–500) | A lap window's sample count is checked against R76's one-segment rule only under `averaging: "none"`, and even then only for *multi*-segment windows. `core::fft::resolve_seg` clamps `nperseg` down to the slice length whenever the slice is shorter than `nperseg`, so a lap window of 1–2 samples (a corrupt/degenerate lap boundary, or two laps recorded ~0 s apart) always resolves to exactly one segment and sails through `check_none_averaging_segments` under every averaging mode. `effective_rate_hz_from_t_us`'s `<2`-sample guard (the one place R76 rejects a too-short record) runs against `ch.t_us` — the **whole channel** — not the sliced window, so it never sees the degenerate window either. Before this task no caller could reach this path (`lap` was always rejected), so this is a new gap this change opens, not a pre-existing one being merely inherited. | Needs a ruling: the brief forbids touching `core::fft` or adding an `IpcErrorKind`, but the fix belongs at the layer that knows the *sliced* sample count, i.e. `fetch_fft_via` itself — check `samples.len()` against a minimum (e.g. reuse the existing `InvalidArgument`/`detail: {"lap": n}` shape, or map a `< 2`-sample slice through `map_fft_error`-style handling) before calling `check_none_averaging_segments`/`welch`. Flag to the lead rather than resolving unilaterally, since it is a scope question (tauri-side minimum vs. widening a core primitive). |

**Verdict rationale:** The core mechanism — window resolution, slicing, ordering of the R76 check against the sliced length, `lap: None` compatibility, and the C3/CHANGELOG paperwork — is all correctly implemented and well tested. The one substantive problem is that this task opens a new, previously-unreachable path for a degenerate (1–2 sample, or even 0-sample) lap window to bypass every one of core's few-sample guards under any averaging mode, because `check_none_averaging_segments` only fires on multi-segment `"none"` requests and `effective_rate_hz_from_t_us`'s `<2`-sample guard checks the whole channel, not the slice actually going into `welch()`. That is a real correctness gap (silent `NaN`/meaningless output rather than a typed error on bad data, which CLAUDE.md §5 forbids), not a style nit, so this is not clean. It does not, however, rise to Critical: it cannot panic (confirmed no index-out-of-bounds/divide-checked path; the Hann/Hamming NaN path is a bad answer, not an unwind), and exploiting it requires an already-corrupt or pathological lap boundary in `session.json`, which the lap-detector output is not expected to normally produce. This needs a ruling from the lead on where the minimum-sample check belongs (tauri vs. widening a core primitive) before a fix lands, since the brief explicitly forbade both touching `core::fft` and adding a new `IpcErrorKind`.

VERDICT: FINDINGS 0 Critical, 1 Major, 2 Minor
