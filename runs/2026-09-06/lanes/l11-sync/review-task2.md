| Severity | file:line | Finding | Fix |
|---|---|---|---|
| Important | `manifest.rs:198-209` (`collect_blobs`), `manifest.rs:262-271` (derived loop) | Blob and derived-channel entries are re-hashed from file bytes read off disk, not trusted from the CAS path/filename that C4 §6 names as the identity key (`"sha256" (= the path itself)`), and which `store::blob::write_blob`'s own doc comment establishes as this crate's CAS convention ("the same hash can only mean the same bytes... trusted without re-reading"). For a corrupted blob (path hash ≠ content hash — exactly what `verify`'s check #1 flags as an `Error` finding), the manifest silently reports an entry keyed on the *wrong* hash: one that doesn't match the file's real serving path (`GET /idl1/v1/blob/<sha256>` would 404 or serve nothing for it), so a sync would neither pull the good copy from a peer nor surface any diagnostic — it just vanishes from view. It also reads every blob and derived-parquet's full bytes into memory only to hash them, which is wasteful at scale (blob store can hold whole session recordings). | Derive `sha256` from the shard+filename path (as `blob_path`/CAS naming already guarantees) and `size_bytes` from `fs::metadata`, not from re-read+re-hash. Let `verify` (which already exists) be the one place that flags a path/content hash mismatch. |
| Important (flag for lead ruling) | `manifest.rs:389-406` (`collect_workbooks`) | The brief's "Key logic" says a workbook whose front matter won't parse is "skipped **and named in the error path**, never silently dropped." The implementation does `let Ok(...) = parse_front_matter(markdown) else { continue };` — no name, path, or reason is recorded anywhere (not in `Manifest`, not in `SyncError`, not even in a log). This is the same pattern `store::catalog::rebuild_catalog` already uses elsewhere in this crate (a `skipped: Vec<String>` collected alongside the main result) — the doc comment on `read_data_parquet_manifest_fields` cites that very module, so the convention was in view. As written this is a silent drop, not "named." Separately, the dispatch's core question: `Manifest`'s only representation of "malformed" is `None`/absence, indistinguishable on the wire from "this file was never created." Task 3 (`plan_sync`, not yet written) will have to treat an entry that disappeared from a peer's manifest as either "delete it here too" or "peer had a hiccup, keep mine" — the manifest schema as built gives it no way to tell those apart. This is inherited from the brief's own `Interfaces` block (no side-channel field is offered), so it is not chargeable as an implementer defect on its own, but it is a real design gap this task should have flagged per CLAUDE.md §1 ("a wrong assumption costs more than a question") rather than silently picking "no side-channel." | Lead ruling needed: either (a) add a minimal side-channel (e.g. `Vec<String>` of skipped/malformed identifiers, `Manifest.errors` or similar, wire-visible or command-layer-only) before Task 3 is written, or (b) rule explicitly that "malformed" and "absent" are meant to be indistinguishable and Task 3's diff must never delete on absence alone (only add/update). Either way this task's brief text ("named in the error path") should be corrected or the code brought into line with it. |
| Minor | `manifest.rs:429-436` (`collect_tracks`), `:451-458` (`collfect_profiles`) | Unlike `WorkbookEntry` (which explicitly tolerates `file_name` ≠ `workbook_id`, keying on the content id per the brief), tracks and profiles are silently **excluded from the manifest entirely** when the file's own embedded id doesn't match its filename stem. This is a reasonable defensive choice but it's an added rule the brief never asked for and no test covers it (the brief's test list has no track/profile-mismatch case). Low impact since `TrackEntry`/`ProfileEntry` carry no `file_name` field to record a rename against anyway. | Note for the lead: confirm this fail-closed behaviour (vs. keying on the embedded id and reporting a rename, like workbooks) is the intended rule for these two classes, and add a test if so. |
| Minor | `manifest.rs:275-283` (`read_data_parquet_manifest_fields` doc comment) | The comment says these three fields "this module has no access to — they are private to that module." That's only half true: `store::catalog::read_data_parquet_session_fields` itself is `pub(crate)` (crate-visible), it is specifically its three struct fields (`importer_version`, `seam_correction_version`, `engine_version`) that lack `pub(crate)`. The duplication is still the right call (widening three fields on an internal struct for one caller is worse), but the comment overstates why. | Reword to "its fields are private, not the function" for accuracy; no code change needed. |

**Verified against C4 §6 (byte-for-byte):** `Manifest{schema_version, generated_at_ms, blobs, sessions, workbooks, tracks, profiles}`; `BlobEntry{sha256, size_bytes}`; `DataParquetEntry{sha256, size_bytes, importer_version, seam_correction_version, engine_version}`; `DerivedEntry{sha256, size_bytes}`; `SessionJsonEntry{sha256, size_bytes, updated_at_ms}`; `SessionEntry{session_id, data_parquet, derived, session_json}`; `WorkbookEntry{workbook_id, file_name, sha256, size_bytes, updated_at_ms}`; `TrackEntry{track_id, sha256, size_bytes, updated_at_ms}`; `ProfileEntry{profile_id, sha256, size_bytes, updated_at_ms}` — all field names and nesting match the spec's JSON example exactly, confirmed by the round-trip test's own JSON-path assertions. Exclusions (`catalog.sqlite`+sidecars, `tmp/` incl. `tmp/quarantine/`, `workbooks/.sync-base/` and any dot-name under `workbooks/`) are each covered by a dedicated test and implemented as "never walked" rather than "walked then filtered," matching the brief. `importer_version`/`seam_correction_version`/`engine_version` are read from `data.parquet`'s Parquet file-level key-value metadata, matching C1 §4.3 exactly (same source `store::catalog::read_data_parquet_session_fields` uses, independently confirmed). `updated_at_ms` sourcing is consistent with the crate's existing conventions: file mtime for `session.json` and workbooks (no such field in either's own content, matches `store::catalog`'s own `file_mtime_ms` use), the file's own embedded field for tracks/profiles (both already carry `updated_at_ms` in their JSON/binary content). Determinism (sort by identity key, run-twice-identical-JSON) is tested and correct. No panics; no `unwrap()` on production data paths (only in test arrange code); typed `SyncError`/`SyncErrorKind`, never `Err(String)`; doc comments present on every public symbol; commit is a single line with no AI attribution; `Cargo.lock`/`Cargo.toml` untouched; CHANGELOG bullet is accurate to the diff.

**Verdict rationale.** The manifest's shape, exclusions, sort order, and metadata sourcing all match C4 §6 and C1 §4.3 precisely, and the 8 tests are well-formed and actually test what they claim. Two Important-severity gaps keep this from CLEAN: re-hashing CAS-identified files instead of trusting the path (a real, if narrow, correctness/perf issue for corrupted or large blobs) and a brief-text requirement ("named in the error path") for malformed workbooks that isn't met by anything in the code — tied to a genuine unresolved design question about how Task 3's diff will treat "absent" vs "malformed" that the brief itself left unaddressed. Neither is data-corrupting today (Task 2 only builds a read-only document), but both should be resolved before Task 3 (`plan_sync`) is written on top of this manifest, since Task 3 is exactly where an absent/misidentified entry turns into a delete-or-keep decision.
