**Verification notes (no findings, checked and clean):**
- **Decode progress DTO** (`tauri/src/session_cache.rs::DecodeProgressEvent`) matches the C3 §3.2 spec text and `app/src/ipc/decode_progress.ts` field-for-field: `session_id: string`, `channel: string`, `done_rows: number`/`u64`, `total_rows: number`/`u64` (never 0 — enforced by the `total == 0` early-return in `decode_reporting_progress` and by `channel_read_tests`), `finished: boolean`.
- **Folding model** (`app/src/state/decodeProgress.ts`): weighted-by-rows aggregation, `total_rows<=0` events dropped, `doneRows` clamped to `[0,totalRows]`. The map empties to `NO_DECODES` exactly when no tracked decode is unfinished (`applyDecodeProgress`'s `anyRunning` check) — verified this can't strand entries: Rust always emits a `finished:true` event once any progress was sent for a decode, including on the error path (`decode_reporting_progress`, tested by `decode_progress_a_failed_decode_still_sends_its_finished_event`), and a decode that never crosses the 200 ms threshold never enters the map at all. No leak found.
- **Timeline drag fix**: `lanePixelX(clientX, laneLeftPx)` is used by both `handlePointerDown` and `handlePointerMove` via the single `pixelXFromEvent` helper, sourced from `event.currentTarget.getBoundingClientRect().left` — the lane div, not the padded container `containerRef`. Confirmed the container has `px-2` padding and the lane fill/handles are rendered as children of the lane div itself (so `left: handles.startPx` is already in the same frame). Both handlers funnel through the one function; the fix is complete, not partial.
- **Chart width**: `resolveChartWidthPx` correctly defaults/clamps/snaps (unit-tested at the boundary values and across a scan). `ChartCell`'s frame is laid out at `width:"100%"` of its column (not the `width` prop) so tile-fetch/plot width and DOM layout width can never diverge, and reporting the measured width from the same rAF-deferred `ResizeObserver` callback that already drives `sendLayout` avoids a second, independently-timed measurement. The `chartWidthNeedsRefetch(fetchedPx, resolvedPx)` gate correctly treats the very first effect run (mount, `fetchedPx===null`) as already covered by the bind effect's own initial fetch at `DEFAULT_CHART_WIDTH_PX`, so it does not double-fetch on mount, and correctly re-fetches on every subsequent resolved-width change in either direction (test: "a column toggle narrowing... re-fetches at the narrower width"). No refetch loop: refetch goes through `runChannelSettle`, which only changes tile data/`chartWindows` state, never the frame's DOM size, so it cannot re-trigger the `ResizeObserver`. The effect is keyed only on `[chartWidthPx]` (a primitive, `Object.is`-compared), so decode-progress or hover-driven re-renders that don't change the resolved width do not re-fire it. Range priority in the refetch path is shared viewport → cell's own last settled window → `initialSpan`, matching the brief.
